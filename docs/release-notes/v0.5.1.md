The flatpak is now something you can actually get — every release carries a ready-built bundle — and it works on Fedora Atomic, where it previously asked for a password on every single tint change.

### Fixed
- **Repeated password prompts on Fedora Atomic** — the setup reported success and then every tint change asked for a password anyway, including the automatic ones at login and after resume, which are exactly the case the setup exists to remove. Fedora Atomic redirects `/usr/local` to `/var/usrlocal`, and `pkexec` resolves symlinks before handing the path to polkit, so the rule — which named only `/usr/bin` and `/usr/local/bin` — never matched what polkit was actually asked about. It now allows the resolved path too, which is root-owned on those hosts and so no weaker a claim than the two already there. The investigation is written up in [docs/fedora-atomic-password-prompts.md](https://github.com/cosmic-nightlight/cosmic-nightlight/blob/v0.5.1/docs/fedora-atomic-password-prompts.md), against Fedora Linux 44.1.7 COSMIC Atomic with polkit 127-2.fc44.2.
  > **Upgrading on Atomic takes one command.** Updating the flatpak does not replace a rule already copied to the host — it has to be installed again. See [Repeated password prompts on Fedora Atomic](https://github.com/cosmic-nightlight/cosmic-nightlight/blob/v0.5.1/flatpak/README.md#repeated-password-prompts-on-fedora-atomic). The helper itself can stay where it is.
- **A brightness change made mid-apply no longer goes missing** — changing brightness while another change was still being applied (in practice, moving both sliders in the same second) could leave the screen and the saved setting describing two different things. Committing a change both queues the work and wakes the app's own watcher, so two requests arrive together; the second only ever checks the temperature, found it unchanged, and concluded there was nothing to do — taking the brightness with it. It did not fix itself either: every later check compared the same two unchanged values and reached the same conclusion, so the screen stayed wrong until the temperature changed or the machine resumed from suspend. The newer values still win, but a change you asked for is no longer cancelled by a check that ran behind it.

### New
- **Every release carries a flatpak bundle** — the sandboxed build existed nowhere a user could reach: the release page had only the `.deb`, and it is not in the COSMIC Store yet. Trying it now means a download and one command rather than generating `cargo-sources.json` and compiling libcosmic yourself. Built by CI on the tag, so it cannot go stale against the `.deb` beside it.
- **The app can be translated** — every word it shows now comes from a message catalog rather than from the code, so adding a language means writing one file: no Rust, and no building the app. Anything a translation leaves out falls back to English message by message, so a partial translation is useful from the day it is started rather than only when it is finished. Message ids are checked against the English catalog when the app is built, so a typo becomes a build error instead of a blank label, and the catalogs travel inside the binary — the `.deb`, the flatpak and a plain `cargo build` all carry their translations with no packaging change. **English is still the only catalog, so nothing on screen changes yet.** See [docs/translating.md](https://github.com/cosmic-nightlight/cosmic-nightlight/blob/v0.5.1/docs/translating.md) for how to add one, including the two packaging files that carry the name and description your software center shows.

### Other
- **The flatpak manifest is pinned to a release tag**, not to the merged branch the sandbox work was done on. cosmic-flatpak builds whatever the source resolves to at build time, so a branch there meant the Store could have shipped anything later landing on it under a released version's metadata.
- Two things a desktop has lying around and a CI runner does not — `eu-strip` and a gdk-pixbuf SVG loader — each failed the flatpak build on the last step of the module, after the entire Rust compile had succeeded. Both are now installed explicitly, found by dispatching the workflow rather than by a failed release.
- Building the flatpak from a working tree no longer means hand-editing a second copy of the manifest and remembering not to commit it — [`flatpak/generate-local-manifest.py`](https://github.com/cosmic-nightlight/cosmic-nightlight/blob/v0.5.1/flatpak/generate-local-manifest.py) derives it from the real one. The advice for regenerating `cargo-sources.json` was also wrong in a way that failed quietly, and now says to regenerate before each build.
- An attended test for the dismissed-prompt backoff, which only misbehaves against a real polkit: it stashes the host helper and rule, runs the flatpak's daemon against one dismissed dialog, and reads the verdict out of the log.

## Install

1. Download **`cosmic-nightlight_0.5.1-1_amd64.deb`** from the Assets section below.
2. Open the downloaded file with the **COSMIC Store** and click **Install**.
   (Or from a terminal: `sudo apt install ./cosmic-nightlight_0.5.1-1_amd64.deb`.)
3. Add the applet to your bar: **COSMIC Settings → Desktop → Panel** (or
   **Dock**) **→ Configure applets → Add applet → Night Light**.

To try the sandboxed build, download **`cosmic-nightlight-0.5.1.flatpak`** and run `flatpak install --user ./cosmic-nightlight-0.5.1.flatpak`. It sets up its host helper the first time you turn the night light on. The `.deb` is still the supported route until the COSMIC Store listing lands.
